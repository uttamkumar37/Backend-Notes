## 3. What → why → when → how

| Concept | What | Why / when | Here |
| --- | --- | --- | --- |
| Repository | Files managed together by Git | Organize and review changes | Enclosing `Backend-Notes` repository |
| Module | Packages sharing a module path and dependency requirements | Version/manage a Go project | This directory's `go.mod` |
| Package | Related source files in one directory | Separate responsibilities | Root command package and `greeting/` library package |
| Import path | Identity used to find a package | Call code outside the current package | `example.com/go-lab/module-basics/greeting` |
| Exported name | Identifier visible outside its package | Define a package's usable API | `greeting.Welcome` starts with uppercase `W` |
| `go.mod` | Module identity, Go baseline, dependency requirements | Review dependency changes | One requirement for a test helper |
| `go.sum` | Checksums for downloaded module versions/metadata | Detect inconsistent dependency content | Real hashes generated by Go |
| Workspace | Several local modules selected together | Develop/test multiple modules locally | `workspace/go.work` selects Lessons 1 and 2 |

The [Go code organization guide](https://go.dev/doc/code) explains module/package organization. A directory named `greeting` does not need its own `go.mod` to become a package; adding one would introduce another module boundary.

### Follow an import to disk

```text
go.mod: module example.com/go-lab/module-basics
                      + /greeting
main.go import: example.com/go-lab/module-basics/greeting
                      ↓
local directory: 02-modules-packages/greeting/
                      ↓
package greeting → exported function Welcome
```

The full import path is not the physical Mac path. Because this package belongs to the active local module, Go finds its source here without downloading it from `example.com`. This is an educational namespace, not a published repository.

Production source files in a package directory normally declare the same package. An external test package named `greeting_test` is a supported testing convention; it checks the public API from outside `greeting`.

## 4. Java / Spring Boot comparison

| Familiar idea | Go equivalent | Difference that matters |
| --- | --- | --- |
| Maven/Gradle project descriptor | `go.mod` | Go includes dependency management in its toolchain; one repository can contain several modules |
| Java package/import | Go package/import path | A Go package consists of files in a directory; the import path combines module identity and relative subdirectory |
| `public` method | Exported `Welcome` | Go uses an uppercase initial letter, not a `public` keyword, for package export visibility |
| A utility class's static method | `greeting.Welcome(...)` | `greeting` is a package qualifier, not an instance or a class |
| Test-scoped comparison helper | `cmp` imported only by `_test.go` | It still appears in normal `go.mod` requirements; there is no separate `devDependencies` section |
| Multi-project IDE workspace | `go.work` | It selects local Go modules; each keeps its own `go.mod` and identity |

## 6. Explain every line and value

| `main.go` line | Explanation |
| --- | --- |
| 1 | `package main` identifies an executable package, as in Lesson 1. |
| 3 | `import (` starts a grouped import declaration. Parentheses contain several package paths; these are configuration for this file, not a function call. |
| 4 | `"fmt"` imports the standard formatting package, supplied by Go. We use it to print the result. |
| 6 | Imports our own library through its full module-based path. Its declared package name is `greeting`, the qualifier used below. The blank line separates standard and other imports for readability. |
| 7 | Ends the import group. |
| 9 | Declares `main`, with no parameters/results, and starts its body. |
| 10 | `investorName := "Asha"` declares a new `string`. The name is fictional and originates in this source literal. It is not loaded from a database, environment, or user account. |
| 11 | Calls exported `Welcome` in package `greeting`. The argument is the current value of `investorName`. Its returned string initializes new variable `message`, so `:=` is appropriate. |
| 12 | `fmt.Println(message)` writes the returned string and a newline to standard output. |
| 13 | Ends `main`; this simple program then exits. |

| `greeting.go` line | Explanation |
| --- | --- |
| 1 | Declares a library package named `greeting`. It has no executable entry point; the command imports and calls it. |
| 3 | This file needs its own `fmt` import for formatting. Importing `fmt` in `main.go` does not make it available in another file. |
| 5 | `//` begins a documentation comment describing exported `Welcome`. It does not run. |
| 6 | `func` declares `Welcome`. Its uppercase `W` makes it accessible to importing packages. Parameter `name` has type `string`; the final `string` after `)` is the return type. There is no method receiver. |
| 7 | `fmt.Sprintf` constructs text, placing `name` at `%s`. `return` sends that string back to the caller and ends this invocation. Nothing is printed in this package. |
| 8 | Ends the function. |

The value flow is source literal `"Asha"` → `investorName` → parameter `name` → returned `"Welcome, Asha."` → `message` → terminal. Function calls are ordinary sequential execution; an import does not call `Welcome` automatically. Go initializes imported packages before entering application `main`, but this package has no custom initialization work.

Here `:=` introduces new local names; `=` would assign an already-declared one. The application code has no pointers, `&`, dereferencing, receivers, or goroutines. `Welcome` returns only a string, so it cannot return an error under this signature. As in Lesson 1, the tiny terminal call intentionally ignores `Println`'s count/write-error results. Empty names are not validated yet; this is a package/module exercise, not a production investor validator.

Go export rules come from the [language specification](https://go.dev/ref/spec#Exported_identifiers). Lowercase does not mean private to one file: unexported names remain accessible from other files of the same package. Import cycles are rejected; keep the direction `main → greeting`, with no reverse dependency.

### Explain the tests

[main_test.go](main_test.go) uses the `Example` pattern from Lesson 1: `package main`, `func Example()`, a call to `main()`, and the `// Output:` expectation `Welcome, Asha.`. No import is necessary because it calls only our package function. It checks the complete program output.

[greeting/greeting_test.go](greeting/greeting_test.go) checks a different supplied investor name:

```go
package greeting_test

import (
	"testing"

	"example.com/go-lab/module-basics/greeting"
	"github.com/google/go-cmp/cmp"
)

func TestWelcomeUsesInvestorName(t *testing.T) {
	got := greeting.Welcome("Mira")
	want := "Welcome, Mira."
	diff := cmp.Diff(want, got)

	if diff != "" {
		t.Errorf("Welcome() mismatch (-want +got):\n%s", diff)
	}
}
```

| Test-file line | Explanation |
| --- | --- |
| 1 | `greeting_test` places the test outside the implementation package. It must import `greeting` and use its exported API, like another consumer. This does not create another module. |
| 3–8 | Grouped imports: `testing` supplies runner state/reporting; our full local import supplies `Welcome`; third-party `github.com/google/go-cmp/cmp` supplies comparison function `cmp.Diff`. The dependency module is `github.com/google/go-cmp`, while the imported package includes `/cmp`. |
| 10 | Test declaration. `t *testing.T` is the runner-provided pointer type explained in Lesson 1. `*` belongs to the type; we neither dereference it explicitly nor create it with `&`. |
| 11 | New string `got` receives actual behavior for fictional `"Mira"`. Using a name different from the program default catches hardcoded `"Asha"` behavior. |
| 12 | New string `want` records the independently expected result. |
| 13 | New string `diff` receives `cmp.Diff(want, got)`: empty if equal, descriptive text otherwise. Argument order matches the diagnostic's `-want +got` convention. This call returns text, not an error. |
| 15 | `if diff != ""` runs the body only for a nonempty difference. `""` is an empty string; `!=` means not equal. |
| 16 | `t.Errorf` marks failure without immediately terminating the test. `\n` in the string literal creates a newline, then `%s` inserts the returned difference text. |
| 17–18 | Close the conditional and test function. |

The dependency's [comparison documentation](https://pkg.go.dev/github.com/google/go-cmp/cmp) describes its behavior. A direct string comparison would suffice for this tiny value; the test helper is included deliberately to learn real dependency metadata and useful diff diagnostics. It stays in test code and is not used by the application's runtime path.

### Read `go.mod` and the real `go.sum`

[go.mod](go.mod) contains:

```go
module example.com/go-lab/module-basics

go 1.27.0

require github.com/google/go-cmp v0.7.0
```

These directives are module configuration, not Go functions. `module` provides the prefix for our package paths. `go` declares the minimum Go baseline; installed 1.27.1 satisfies it. `require` adds a dependency module and version requirement. `v0.7.0` means major 0, minor 7, patch 0; major-zero APIs can change incompatibly. For this graph, that is the selected version. In larger graphs another requirement can select a higher version, so `go.mod` is not an exact universal lockfile. See the [go.mod directive reference](https://go.dev/doc/modules/gomod-ref).

The helper is directly imported by this module's tests, so it is a direct requirement even though production code does not use it. A requirement marked `// indirect` usually describes a module not directly imported by this module's own packages/tests; it is still part of dependency management. Read [Go's dependency management guide](https://go.dev/doc/modules/managing-dependencies) before changing requirements casually.

[go.sum](go.sum) was generated by `go mod tidy` and contains two real entries:

```text
github.com/google/go-cmp v0.7.0 h1:wk8382ETsv4JYUZwIsn6YpYiWiBsYLSJiTsyBybVuN8=
github.com/google/go-cmp v0.7.0/go.mod h1:pXiqmnSA92OHEEa9HXL2W4E7lf9JzCmGVUdgjX3N/iU=
```

Each line records a module path, version/content kind, and `h1:` checksum. The first covers module content; the `/go.mod` entry covers its module metadata. These are integrity checks, not secret keys, version-selection commands, or encryption. Do not invent/edit hashes manually. In general, entries can include older versions or metadata needed by dependency loading, so this file is not simply a list of current imports. Commit the generated dependency files with the source; the [module reference](https://go.dev/ref/mod#go-sum-files) explains checksum records.

| Part | Meaning |
| --- | --- |

| `go list -m all` | List the main module and selected dependency modules. `-m` asks about modules instead of packages. |
| `go mod verify` | Detect post-download modification of cached module content; it is not a vulnerability scan or substitute for tests. |

Downloads use your ordinary public Go module configuration; no office infrastructure is required. There is no global SDK/tool configuration change.

The program prints:

Now open [workspace/go.work](workspace/go.work):

```go
go 1.27.0

use (
	..
	../../01-first-program
)
```

This is workspace configuration. `go` is the minimum workspace baseline. `use (` begins a list of local module directories, and `)` closes it. Paths are resolved relative to **this go.work file**: `..` means Lesson 2's root; `../../01-first-program` means Lesson 1's root. Each already has its own `go.mod`. They are two independent programs grouped for development, not two newly communicating services.

From the Lesson 2 root, run:

```bash
cd workspace
GOTOOLCHAIN=local GOWORK="$PWD/go.work" go env GOWORK
GOTOOLCHAIN=local GOWORK="$PWD/go.work" go test -v ../... ../../01-first-program/...
```

`cd workspace` selects the folder containing the supplied file. `$PWD` expands to your current directory; the quoted expression produces its absolute `go.work` path. `GOWORK` explicitly selects that file for this command. `go env GOWORK` prints the selected path; normally Go can also discover workspace files in the current/ancestor directories when no override is set. The test command explicitly selects package patterns in **both** member modules. It runs the four supplied checks across Lessons 1 and 2; learner-added tests may increase the count.

The workspace folder itself has no package. `go test ./...` from there does not mean “test every member,” because `./...` describes directories under that folder. Use the explicit patterns above. Return to the module root with `cd ..` and use `GOWORK=off` for the independent check. See the [official workspace tutorial](https://go.dev/doc/tutorial/workspaces).

For a new, empty workspace folder, `go work init .. ../../01-first-program` would create this file; it is already supplied, so do not reinitialize it. `go work use PATH` adds a module directory. There is no need to run `go work sync` here: that can update member module requirements and should be a deliberate action. A workspace can select local module code during development; it does not replace a module's published dependency metadata. See the [Go team's workspace explanation](https://go.dev/blog/get-familiar-with-workspaces).

This exercise intentionally commits a workspace with relative paths for reproducibility. Repository policies vary for personal workspaces. `go.work.sum` can hold additional workspace checksum information when needed; it is not required for this supplied graph. Do not assume a missing sum file is always an error.

## 12. Recap and microservice connection

An import resolves a package, and that package belongs to a module. Exports define what callers may use. Dependencies include tests and come with reviewable metadata/checksums. A workspace groups local modules while leaving their identities intact.

In an office repository, start with `go.mod`, import paths, package directories, and `go env GOWORK` before guessing why a build differs between machines. A microservice can contain many packages; several service binaries can share one module. Avoid creating modules just because a new folder or HTTP endpoint appears.
